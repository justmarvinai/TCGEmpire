# TCGEmpire — Architecture

> Status: **approved plan** (owner decisions of 21 Nov 2026 included). Items marked **SPIKE** are verified
> in the first days of alpha_01 before anything is built on them; each has a stated fallback.
> Guiding rule from the owner: **build lean** — the simplest thing that meets the design, no speculative
> abstractions, low token use.

## 1. Constraints that shape everything

| Constraint | Consequence |
|------------|-------------|
| Must run on **Vercel Hobby** + **Supabase Free (Nano compute)** | No per-request server code on Vercel; all game logic inside Postgres; light, lazy simulation; strict data retention. |
| Private game for one friend group (**2–10 players**, Q-3) | One world, no sharding, no matchmaking; one shared invite code. Everything must work with two players, so NPCs carry the market. |
| Multiplayer economy with betrayal and toplists | Server-authoritative: the browser sends intentions, never results. |
| Developed mostly by AI agents in short sessions | One language per layer, one source of truth per rule, fast offline test loop, strict conventions. |
| Code-generated pixel art, concentrated on cards and products | Art is code, rendered at build time into atlases, reviewed through generated contact sheets. Little pixel art elsewhere. |

## 3. Stack

| Layer | Choice | Why |
|-------|--------|-----|
| App | **Vite + React 19 + TypeScript (strict)**, single-page app | The game is fully behind login, client-heavy and animation-heavy. A SPA has no hydration pitfalls, no server runtime to pay for, instant navigation, and a very fast dev loop. SSR/SEO bring nothing here. |
| Routing / data | **React Router** (declarative routes), **TanStack Query** (server state), **Zustand** (UI state) | Small, well known. |
| Validation | **Zod 4** schemas for every RPC response | Contract between SQL and client, checked in tests. |
| Styling | **Tailwind CSS 4** with our own design tokens only (default palette removed) | Consistent look, no ad-hoc colours. |
| UI primitives | **Radix UI** (dialog, popover, tooltip, tabs …) | Accessible behaviour, our own visuals. |
| Animation | **Motion** + CSS; canvas for particles and mini-games | Transform/opacity only. |
| Audio | Own tiny **WebAudio synth** (parameter presets, no audio files) | "Everything generated by code", zero asset weight. |
| Pixel art | Own **painter toolkit** (TypeScript) → build-time PNG atlases | See `ART_DIRECTION.md`. |
| Backend | **Supabase**: Postgres + PL/pgSQL RPCs, Auth, Realtime, pg_cron | Everything on the free plan; no invocation limits on RPCs; transactions for free. |
| Tests | **Vitest**; **PGlite** (in-process Postgres) for SQL logic, contracts and economy simulation **SPIKE**; **Playwright** for end-to-end and screenshots | No Docker needed; runs in any agent session and in CI. |
| Tooling | pnpm, ESLint, Prettier, GitHub Actions, own psql migration runner | — |

Text is German only, kept in typed message modules (`src/texts/`), not in components. No i18n library.

**Rejected alternatives** (details in `DECISIONS.md`): Next.js (server features unused, extra complexity);
game logic in Vercel functions (the Hobby plan's 4 h of active CPU and 1M invocations per month are a
real ceiling for a per-minute tick plus every player action; exceeding them pauses the project);
Supabase Edge Functions for logic (500k invocations per month, cold starts, second language runtime);
rules duplicated in TypeScript and SQL (drift between the two is a known source of bugs).

## 4. Core principles

1. **Server authority.** Money, items, EP, timers and randomness change only inside the RPC functions.
   The client has no table access at all.
2. **One source of truth per rule.** Formulas exist only in SQL. The client displays what RPCs return
   (including previews like "cost of next level"). The only client-side maths is interpolating time
   (a bunker counter ticking between syncs from a server-provided rate and timestamp).
3. **Lazy time.** Anything that is "X per hour" or "done at time T" is computed from timestamps when it is
   read or claimed (bunker, shifts, grading, shipping). No background job touches idle players.
4. **One tick.** A single cron job runs `private.tick()` each minute. It dispatches the few systems that
   truly need a clock (prices, NPC traders, restocks, events, auctions, company cycles, cleanup), each in
   its own sub-transaction with its own interval and catch-up cap. A failing system is logged and skipped,
   never blocking the others.
5. **Content is code.** Cards, sets, jobs, upgrades, quests, events and balance values are TypeScript
   data in `content/`. A generator writes them into `content.*` tables. The client imports the same files
   for names, texts and art. Balance values can additionally be overridden live by the admin.
6. **Everything is an event.** Game actions call `private.emit(player, event, amount, meta)`; quests,
   achievements, statistics and the feed subscribe to it. New quests need no new code.
7. **Modifiers are data.** Upgrades, skills, perks, decor, set bonuses, buffs and events all produce rows
   in one modifier format; a single function resolves a player's effective stats.
8. **Time is injectable.** SQL never calls `now()` directly but `private.now()`, which tests and the
   simulation harness can move.
9. **Game-set money is Basis-€ × Preisniveau.** Config holds base amounts; `private.eur()` is the only
   way to turn them into real cents (`ECONOMY.md` §4).

## 5. Anatomy of a write action

```
client:  rpc('market_buy_listing', { request_id, listing_id })        ← request_id = fresh UUID
server:  public.market_buy_listing(p_request_id uuid, p_listing_id uuid) returns jsonb
           1. v_player := private.require_player()            -- auth.uid() → player row, or error
           2. replay?  := private.request_begin(...)          -- same request_id → return stored answer
           3. private.rate_limit(v_player, 'market', ...)
           4. lock rows in fixed order (listing, buyer, seller) FOR UPDATE
           5. validate (level gate, funds, capacity, state)   -- failures: private.fail('code')
           6. private.money_add(...) for both sides, fee as sink   -- writes ledger rows
           7. move items, write domain rows
           8. private.emit(...)  → quests, achievements, feed
           9. private.notify(...) → realtime ping to affected players
          10. return private.request_done(..., jsonb result incl. changed state)
client:  Zod-parse the answer → update query cache from the returned state → play the animation
```

Conventions: `SECURITY DEFINER`, `set search_path = ''`, execute granted to `authenticated` only,
errors as stable codes (`TE001 insufficient_funds` …) that map to German messages on the client,
`jsonb` results in snake_case, money as integer cents. No Postgres enum types (text + check constraints
instead, so values can be added in the same migration). No `UPDATE`/`DELETE` without `WHERE`.

## 6. Time and simulation

| System | Model | Interval | Notes |
|--------|-------|----------|-------|
| Geldbunker, shifts, energy, grading at NPC graders, shipping, buffs | Lazy from timestamps | on read / claim | Zero cost while offline. |
| Market prices | Tick | 5 min | ~350 cards + products updated in one statement; snapshot cached for all readers. |
| NPC traders | Tick | 1 min, small action budget per run | Seeded randomness; budgets refill daily. |
| Retail restocks | Tick | at scheduled times | Shared stock rows per store. |
| Events | Tick | 10 min roll | Global and personal; admin can trigger. |
| Auctions, pack battle timeouts | Tick | 1 min | Plus resolution on access. |
| Companies | Tick | 10-minute cycles | One sub-transaction per company; catch-up capped, oldest first. |
| Toplists, rivals | Tick | 10 min snapshot | Lists are read from the snapshot, never computed per request. |
| Daily reset: quests, Tagesereignis, Preisniveau, NPC budgets | Tick | 00:00 Europe/Berlin | One system, idempotent per day. |
| Cleanup and retention | Tick | hourly | See §9. |

The tick takes an advisory lock; if a run is still active the next one skips. Every run writes a row to
`game.job_runs` (duration, errors); the admin console shows it.

## 7. Staying in sync

- **`sync(cursors)`** is the one polling call: every 15 s while the tab is visible (none while hidden,
  one immediately on focus). It returns the server time, version counters per state area, new
  notifications, new feed items and due timers. The client refetches only the areas whose counter changed.
- **Realtime Broadcast** makes things instant where it matters: world channel (Grail pulls, events,
  restocks, feed), a private channel per player (notifications, "your listing sold"), one channel per
  pack battle and box break, chat. Sent from the database inside the same transaction.
- **Presence** on the world channel shows who is online.
- The game is fully playable with polling alone; Realtime is an enhancement, never a dependency.
- Countdown timers use the server time offset, never the device clock.
- Pack battles and box breaks: the server decides everything first and returns a timeline; clients replay
  it against the server clock. Cards of later rounds are not sent before their reveal time.

## 8. Security

- **Login:** Supabase gives every browser an anonymous auth user. Our RPCs `join` (e-mail, username,
  password, **shared invite code**), `login` (e-mail or username) and `logout` bind that session to a player.
  Passwords are bcrypt hashes; wrong passwords are counted and lock the account for a few minutes. The invite
  code is one code for everybody (Q-4): the first account sets it, it is stored hashed. The e-mail (Q-31) is a
  second login name only: unique regardless of case, never verified, never mailed, stored next to the password
  hash in `game.credentials` so no player document carries it; only its owner reads it (`account_get`).
- **Exposure:** schema `public` contains nothing but the RPC functions, each granted to signed-in
  sessions only. Tables live in unexposed schemas, additionally with RLS enabled and no policies (deny
  all) as a second wall. No service-role key anywhere in the client.
- **Admin:** the first account created gets the admin flag (Q-5); it plays normally and additionally sees
  the admin console. Admin RPCs check the flag and write to an audit log. If that account is deleted, the
  oldest remaining account becomes admin.
- **Account reset and deletion** (Gefahrenzone) are RPCs that cancel open business, destroy the account's
  items and anonymise old feed and chat entries in one transaction.
- **Realtime:** private channels authorised by policies on `realtime.messages`.
- **Privacy:** no real personal data is stored beyond the chosen username; the site sends `noindex` and
  is not linked anywhere.
- **Cheating:** mini-game scores are capped by what is possible; rate limits per player and action;
  idempotent requests; all randomness server-side.

## 9. Free-plan budget

Limits as checked in November 2026 (re-verified in the alpha_01 spike):

| Resource | Limit | Our plan | Estimate at 10 active players |
|----------|-------|----------|-------------------------------|
| Supabase database | 500 MB | Stacked bulk inventory; thinned price history; ledger details 14 days then daily sums; chat 5.000 messages; notifications 30 days; request journal 3 days; job runs 7 days | < 120 MB after a year |
| Supabase egress | 5 GB / month | Catalog and art ship from Vercel, not the DB; compact RPC answers; sync only when visible | < 1.5 GB |
| Supabase compute (Nano, shared CPU, 0.5 GB RAM) | — | Lazy timers; 1 light tick per minute; cached snapshots for global reads; indexes on every foreign key and filter | Tick < 50 ms typical |
| Realtime | 200 connections, 100 msg/s, 2M messages / month | One socket per tab; event-driven messages only; pack battles are replayed, not streamed | < 400k messages |
| Project pause | after 7 days without activity | Daily keep-alive request from GitHub Actions | — |
| Auth e-mails | very low send limit | No e-mail flows at all | 0 |
| Vercel Hobby | personal, non-commercial use; function CPU/invocation limits | Static files only; no functions | Far below limits |

A size report (table sizes, row counts) is part of the admin console, with warnings at 60 % of any limit.

**Measured in alpha_12** (`pnpm tsx sim/size.ts 3`: 10 players, a tick every 5 minutes, hourly vacuum like autovacuum;
PGlite runs in WebAssembly, so the times are an upper bound for Supabase):

- **Tick:** 150 ms on average, p95 220 ms, max 330 ms. The market system takes 134 ms of it (362 prices and their
  history rows every 5 minutes), every other system stays under 25 ms. One tick a minute leaves plenty of room.
- **Price history:** 120–160 bytes per row with its index. With the thinning it levels off at about 860 rows per item
  (≈ 45 MB for the four sets), then grows by one row per item and day (≈ 20 MB a year). Each new set adds about 25 %.
- **Job runs:** about 4.150 rows a day, kept 7 days (≈ 3 MB). Without vacuum the `prices` table bloats quickly
  (60 MB in two days in PGlite); Supabase's autovacuum keeps it at a few MB.
- **Per player** (`pnpm sim 20`, one bot playing 150 minutes a day, no retention jobs): the request journal is by far
  the biggest table, about 4 MB a day for this very busy bot (it keeps the replay answer of every write). Since alpha_12
  it is kept one day instead of three (decision 108), so ≈ 4 MB standing per very active player; ledger, cards and
  quests stay well under 1 MB a week. **Estimate after a year at 10 active players:** ≈ 45 MB price history + 20 MB
  growth + ≈ 40 MB journal + < 20 MB other player data ≈ 125 MB, a quarter of the free 500 MB.
- **Frontend:** about 270 kB of JavaScript (gzip) at start: React, Radix and the UI kit ≈ 100 kB, texts, content and
  contracts ≈ 150 kB. Every other page loads its own chunk (≤ 10 kB). The local mode's in-browser Postgres (≈ 290 kB)
  only loads without Supabase keys. Card atlases load per set on demand (135–175 kB each, products 46 kB);
  re-encoding them as palette PNGs saved only 3 %, so they stay as they are.

## 10. Testing and local development

| Level | Tool | What it proves |
|-------|------|----------------|
| SQL logic | Vitest + PGlite, real migrations, injectable clock, fixed random seed | Every RPC: happy path, each error code, idempotency, locks, limits. |
| Contracts | Same run: every RPC answer is parsed with the client's Zod schema | SQL and client agree; a schema without a test fails the build. |
| Invariants | After every test: no negative balances, ledger sums match balances, capacities respected | No money or item leaks. |
| Economy | Simulation harness with bot players (see `ECONOMY.md` §13), kept small | Pace and balance targets. |
| Art | Atlas build + rules (palette size, stray pixels, silhouette size) + contact sheets for review | Art quality gates for cards and products. |
| UI | Playwright smoke tests against **local mode**; screenshots at 1440 px per feature, 390 px once per milestone | Flows work; visual review without burning tokens. |

**Local mode (SPIKE):** with no Supabase keys configured, the app runs the *same SQL* in PGlite inside
the browser (migrations + seed + a small shim for auth, cron and realtime). `pnpm dev` is then a complete
single-player game with a "switch player" dev tool, and Playwright tests need no backend.
*Fallback if PGlite cannot run our SQL:* local Postgres binaries + PostgREST for tests and e2e; game
logic stays in SQL either way.

## 11. Environments and deployment

| Environment | Frontend | Database |
|-------------|----------|----------|
| Local | `pnpm dev` (local mode) | PGlite in the browser |
| Production | Vercel, deploys from `main` | The one Supabase project |

- **Migrations:** plain SQL files in `supabase/migrations/`, applied by `scripts/db-migrate.sh` (psql)
  from a GitHub Action after tests pass. `private.migrations` is the ledger of what ran. One short
  transaction per file. No hand-maintained copies, no megabyte bundles. When Actions cannot run (their free
  monthly amount is shared by all of the owner's private repositories), `scripts/db-migrate-api.sh` applies the
  same files with the same ledger over the Supabase Management API (HTTPS, an access token), only after the
  owner's go.
- **Content seed:** generated SQL, applied only when its hash changed. Admin live overrides are stored
  separately and survive deploys.
- **Order:** database first, then frontend; RPC changes are backwards compatible for one release, and the
  client shows "Neue Version verfügbar — neu laden" when the server's version is newer.
- **Owner setup, once** (Q-2): `docs/SETUP.md` — Supabase project (Frankfurt, anonymous sign-ins on, Cron enabled,
  Realtime "Allow public access" off), Vercel project, three GitHub secrets (publishable key, not the secret key).
- **Alpha data policy** (Q-21): during alphas a migration may reset game data when needed; it is announced
  in the changelog.

## 13. Risks and spikes

| Risk | Mitigation |
|------|------------|
| PGlite cannot run parts of our SQL (extensions, roles) **SPIKE** | Shim layer for Supabase specifics; fallback to Postgres binaries + PostgREST. |
| PL/pgSQL grows unwieldy | Generic engines (modifiers, events, quests, timers); one file per feature; strict template for RPCs; tests per function. |
| Nano compute too weak | Lazy model; tick budget; snapshots; measure tick duration from day one. |
| Art volume and quality | Toolkit first, contact-sheet review loop, hero-art priority, see `ART_DIRECTION.md` §7. |
| Balance | Simulation harness and ledger dashboard before each alpha. |
| Scope | Roadmap with must/should; each alpha is playable on its own. |
| Platform limits change | Limits re-checked at each release; budget table kept current. |

# TCGEmpire — Decisions (ADR log)

Short records of decisions that are expensive to change. New decisions are appended; a changed decision
gets a new entry that names the one it replaces. Status values: **proposed** (plan phase, awaiting the
owner's go), **accepted**, **replaced**.

All entries below are **proposed** until the plan is approved.

| # | Decision | Reason | Consequence / fallback |
|---|----------|--------|------------------------|
| 001 | The client is a **Vite + React + TypeScript single-page app**, hosted as static files on Vercel. | The game is fully behind login, client-heavy and animated; server rendering adds cost and pitfalls without benefit. Static hosting cannot exceed Hobby function limits. | No server-side secrets in the frontend. Anything privileged lives in the database. |
| 002 | **All game logic lives in Postgres functions** (PL/pgSQL), called as RPCs. | Free plan has no RPC invocation limits; transactions and locking for free; no cold starts; one authoritative place. | SQL volume is high; mitigated by engines, templates and tests. |
| 003 | **Rules are implemented once.** The client never recomputes outcomes or costs; it shows what RPCs return. | Two implementations of a rule drift apart and show players wrong numbers. | Previews are RPC answers. Offline/dev play uses the same SQL (ADR-008). |
| 004 | Money is `bigint` **cents**, capped at 9 × 10¹⁵; rates in basis points; no floats stored. | Exactness in SQL and as JSON numbers in the browser. | Exponential formulas compute in `numeric` and clamp. |
| 005 | **Open economy with a full ledger**: every money change goes through one function with a reason code. | Sources and sinks must be measurable to balance an incremental game. | Admin dashboard and simulation read the same reason codes. |
| 006 | **No secular inflation mechanic.** Prices keep real-world scale; value growth comes from scarcity, market cycles and prestige. | Real-feeling prices are part of the humour and easier to understand. | Late-game money is absorbed by exponential sinks and scarce items. |
| 007 | **Lazy timers** for everything idle; **one tick dispatcher** per minute for the few clock-driven systems, each isolated in a sub-transaction with catch-up caps. | Nano compute is small; idle players must cost nothing; one failing system must not stop the rest. | Tick duration and errors are logged and shown to the admin. |
| 008 | **Tests and local play run the real SQL in PGlite** (in-process Postgres); the app has a local mode without Supabase. *Spike in alpha_01.* | Fast agent dev loop without Docker; e2e without a backend; no second implementation. | Fallback: Postgres binaries + PostgREST locally. |
| 009 | **Polling `sync` call + Realtime Broadcast as enhancement.** | Works even if Realtime is unavailable; keeps the 2M messages/month budget safe. | Countdown timers use the server clock offset. |
| 010 | **Content as code**: TypeScript data in `content/` → generated seed → `content.*` tables; admin overrides stored separately. | One place to edit; typed; client and server share it; deploys never wipe live tuning. | Seed applied only when its hash changes. |
| 011 | **Inventory model**: bulk cards as stacks, hits and slabs as individual copies with hidden quality values. | Keeps the database small while giving every valuable card an identity. | A bulk card becomes a copy when graded. |
| 012 | **Pixel art is code**, rendered at build time into PNG atlases; an own painter toolkit with a mandatory visual review loop. | "All art generated by code" at high quality needs tooling and eyes on the result, not hand-typed pixel grids. | Atlases are build outputs; art source is lazy-loaded per set. |
| 013 | Card text is drawn with **own bitmap fonts inside the image**. | Authentic pixel look; cards are shareable images. | Automatic condensing for long German names. |
| 014 | **German** for all player-facing text; **English** for code, comments, commits and docs. | Friends are German; tooling and agents work best in English. | Texts live in typed message modules, never in components. |
| 015 | **Username + password + single-use invite code**; no e-mail flows. | Zero setup for friends; free-plan e-mail limits are tiny; keeps strangers out. | Discord login can be added later (Q-4). |
| 016 | Clients have **no table access**: only schema `api` is exposed; RLS on with no policies everywhere. | Smallest possible attack surface; no policy maintenance. | Reads are RPCs returning page documents. |
| 017 | **No Postgres enum types**; text + check constraints. | Enum values cannot be used in the transaction that adds them. | Slightly less type safety, offset by tests. |
| 018 | **Injectable clock and seedable randomness** in SQL. | Deterministic tests; accelerated simulation; no time-of-day flaky tests. | `now()` and `random()` are never called directly in game functions. |
| 019 | **Migrations via Supabase CLI from CI**, one transaction per file, tests first. | A proper migration ledger from day one; no manual copies. | Fallback: generated SQL file for the SQL editor if the owner prefers (Q-2). |
| 020 | **Version scheme**: `0.0.1-alpha_NN` per milestone until the full release `0.0.1`. | Owner's rule. | Changelog entry and in-game patch notes per alpha. |
| 021 | **Real brands and public figures as private parody**, under the house rules in `HUMOR.md` §2; all names swappable in content. | Owner's wish; the game is private and invite-only. | The site is `noindex`; no public distribution. |
| 022 | **Desktop-first**, responsive down to 390 px without being designed for phones. | Owner's wish. | Mobile polish is not a release criterion (Q-14). |
| 023 | **Set lifecycle is manual.** No set enters or leaves print automatically. | Owner's rule. | Admin console action + audit log. |
| 024 | **Hostile player actions are capped**: daily loss cap, only uncollected bunker money is stealable, every action has a counter. | Betrayal should create stories, not make friends quit. | Intensity is one config value (Q-7). |
| 025 | Sets are curated to **~85 cards** with the game's own seven tiers; every beloved card stays. | Owner's 30–100 rule; art effort; long collection chase. | Lists in `docs/sets/`. |
